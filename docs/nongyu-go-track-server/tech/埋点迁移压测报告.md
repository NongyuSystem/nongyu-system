# Track：Go → Node 迁移最小验证报告

| 项   | 内容                                                                    |
| ---- | ----------------------------------------------------------------------- |
| 日期 | 2026-08-29                                                              |
| 机器 | Track 独立机（约 2C / 1.7GiB，整机只跑埋点相关）                        |
| 目的 | 验证「千人规模写入」下，用 Node+SQLite 替换现网 Go Track 是否资源可接受 |
| 范围 | **仅写入 ingest**；不含管理端查询；不与业务 Node 同机                   |
| 存储 | SQLite 不变                                                             |

原始产物目录：`scripts/track-migration-bench/out/`

---

## 1. 负载设计（高于预估峰值）

| 参数             | 值                                                                             | 说明                                   |
| ---------------- | ------------------------------------------------------------------------------ | -------------------------------------- |
| 目标 RPS         | 30 batch/s                                                                     | 千人粗估峰值约 20–50 batch/s，取中高档 |
| 每批事件         | 40                                                                             | 接近 App 批大小上限（硬限 100）        |
| 等效写入         | ≈ **1200 events/s**                                                            | 约 400 events/s 预估峰值的 3 倍        |
| 时长             | 180s × 2（Go / Node 各一轮）                                                   |                                        |
| 接口             | `POST /v1/internal/events`                                                     | 跳过 presence 回写，避免干扰业务机     |
| 成功标准（预设） | 成功率 ≥ 99.9%；p95 &lt; 200ms；RSS 峰值 &lt; 300MB；CPU 均值 &lt; 50%（单核） |                                        |

说明：现网 Go 默认单 IP 约 300 req/min，无法直接打满 30 RPS。本轮 Go 使用**临时高限流二进制**（测完已恢复原二进制）。

---

## 2. 对照对象

|        | Go（现网能力）                              | Node PoC                                   |
| ------ | ------------------------------------------- | ------------------------------------------ |
| 进程   | 完整 `nongyu-track`（聚合/在线扫描等仍在）  | 最小写入服务：`health` + `internal/events` |
| 运行时 | Go 静态二进制                               | Node.js 22.18 + `node:sqlite`              |
| 库文件 | 生产 `track.db`（测后删除 `loadtest_%` 行） | 独立 `poc-track.db`                        |

> Node PoC **不是**完整功能对等实现（无 JWT App 通道、无日聚合任务、无 rate limit、无 usersync）。它回答的是：**同机、同 SQLite、同写入强度下，Node 运行时 + 落库是否成为瓶颈。**

## 3. 结果摘要

### 3.1 写入表现

| 指标         | Go          | Node PoC    |
| ------------ | ----------- | ----------- |
| 发送 / 成功  | 5391 / 5391 | 5392 / 5392 |
| 成功率       | **100%**    | **100%**    |
| 实际 RPS     | 29.6        | 29.6        |
| 约写入事件数 | 215,640     | 215,680     |
| 延迟 p50     | 3.73 ms     | 1.25 ms     |
| 延迟 p95     | 5.07 ms     | 1.73 ms     |
| 延迟 p99     | 11.67 ms    | 6.43 ms     |
| 延迟 max     | 18.09 ms    | 15.34 ms    |

两者均远优于「p95 &lt; 200ms」验收线。

### 3.2 内存 / CPU（压测过程采样）

| 指标                     | Go                       | Node PoC             |
| ------------------------ | ------------------------ | -------------------- |
| 压测前 RSS（约）         | ~20 MB（原进程空闲基线） | ~54 MB（PoC 刚启动） |
| 压测中 RSS 均值          | **~54 MB**               | **~67 MB**           |
| 压测中 RSS 峰值          | **~62 MB**               | **~68 MB**           |
| 压测中 CPU 均值（单核%） | **~10.4%**               | **~2.5%**            |
| 压测中 CPU 峰值          | ~13%                     | ~6.5%                |

换算：峰值 RSS 都在 **70MB 以内**，相对 1.7GiB 机器可忽略；CPU 远低于 50% 线。

### 3.3 验收对照

| 验收项   | 标准       | Go           | Node PoC     |
| -------- | ---------- | ------------ | ------------ |
| 成功率   | ≥ 99.9%    | 通过         | 通过         |
| p95 延迟 | &lt; 200ms | 通过（5ms）  | 通过（2ms）  |
| RSS 峰值 | &lt; 300MB | 通过（62MB） | 通过（68MB） |
| CPU 均值 | &lt; 50%   | 通过（10%）  | 通过（2.5%） |

## 4. 结论（面向迁移决策）

1. **在「高于千人预估」的写入强度下，Node+SQLite 写入 PoC 完全达标**，未出现错误、排队爆炸或内存失控。
2. **Go 相对 Node 的内存优势存在，但量级很小**（压测峰值大约 62MB vs 68MB；空闲完整 Go ~20MB vs 业务向 Node 常驻更高——完整 Node Track 预计仍远低于 2G 机器压力）。
3. **性能不足以构成「必须保留 Go」的理由**；在农屿规模下，更关键的是统一 TypeScript 后的开发/运维成本。
4. 本报告**支持「可以迁」的性能侧结论**；落地仍需工程工作：补齐 App JWT 上报、幂等、presence、聚合任务、限流与发布切换，而不是再怀疑 Node 扛不住写入。

---

## 5. 局限（读报告时请带上）

- Node 侧是 **最小 PoC**，完整移植后 RSS/CPU 会高于本轮数字（多中间件与定时任务），但按本次余量，涨到 150–250MB 量级通常仍可接受。
- Go 侧带完整后台任务；Node PoC 没有，CPU 对比略偏向 Node。
- 压测为本机 loopback，不含公网 TLS/Nginx；真实用户延迟会叠加网络，但不改变「服务端算力是否够」的结论。
- 未测管理端查询（按你的范围排除）。

---

## 6. 建议的下一步（若决定迁移）

1. 在 `nongyu-node-server` 或独立 `nongyu-node-track` 中按现网契约实现完整 ingest（优先 SQLite）。
2. 影子流量 / 双写一小段时间，再切 App `TRACK_BASE_URL`。
3. 下线 Go Track 机或改作别用。

压测脚本保留在：`scripts/track-migration-bench/`。
