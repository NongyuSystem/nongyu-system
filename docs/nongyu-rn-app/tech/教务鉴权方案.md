# 教务鉴权方案

> 状态：**已切换统一身份认证（2026-10-24）**；旧口令链路已于 2026-10-23 被教务下线  
> 适用范围：`apps/nongyu-rn-app` 教务相关能力  
> 依据：教务处《关于调整教务管理系统登录方式的通知》（2026-10-23）+ 平台实测；实现基于 `nongyu-tool-jiaowu`
> 已验证细节见 §8 / §9，后续改登录以 §9 为准

## 1. 目标

- 教务会话与农屿 App Token **分层**：教务 Cookie 只服务教务抓取；App Token 服务自家后端。
- 教务密码仅存客户端敏感存储，**不上传** Node。
- 登录走学校统一身份认证（川农 e 认证），**图形验证码由用户读图输入**，不做 OCR。

## 2. 角色与依赖

| 层       | 职责                                          | 载体                                                                          |
| -------- | --------------------------------------------- | ----------------------------------------------------------------------------- |
| 教务会话 | 访问需登录的教务 HTML 接口                    | `nongyu-tool-jiaowu`：`getJiaowuCaptcha` / `jiaowuLoginByCas` / 模块内 Cookie |
| 农屿身份 | 登录即注册、单设备等                          | Node `POST /api/app/auth/login`（只交档案，不交教务密码）                     |
| 本地敏感 | 学号 + 教务密码（用于预填，不再用于静默重登） | `expo-secure-store`                                                           |
| 本地会话 | App Token、档案摘要、可选 ASP Cookie 备份     | Zustand + MMKV（Cookie 非密码级，可 MMKV）                                    |

## 3. 主流程（统一身份认证）

```text
进入登录页
  → getJiaowuCaptcha()
       · GET https://auth.sicau.edu.cn/api/v1/captcha?appid=<教务 appid>
       · 解密响应体 → data:image/png;base64,...，连同 uuid 交给界面
  → 用户输入学号 + 密码 + 看图输入验证码
  → jiaowuLoginByCas({ studentId, password, captchaCode, captchaUuid })
       · GET caslogin.asp（建立 ASP 会话）
       · POST /api/v1/cas/login（appid / code / number / password / uuid）
       · 解密 → { callbackUrl, st, users[0].id }
       · GET callbackUrl?ticket=<st>:<userId>&userId=<userId> → 取 ASPSESSIONID*
       · 成功：工具内 setCookie
  → getPersonalInfo()
  → POST 农屿 /api/app/auth/login（档案字段，无密码）
  → 持久化
       · SecureStore：学号、教务密码（仅预填）
       · 会话 Store：档案、App Token、isAuthenticated
       · （可选）持久化当前 ASP Cookie，缩短冷启动重登
```

**登录失败一律换一张验证码**：验证码是一次性的，失败后旧图作废，
不换图会让用户反复提交同一张废图（`jiaowuLoginByCas` 返回 `needRefreshCaptcha`）。

冷启动：

```text
SecureStore 读学号/密码 → 仅用于表单预填
  → MMKV 恢复 ASP Cookie → setCookie(cookie)
  → MMKV 恢复档案摘要 + App Token → 写入 Zustand 会话
  → 业务请求若会话过期：抛 JiaowuSessionExpiredError → 引导用户重新登录（必须重新输验证码）
```

> ⚠️ 与旧方案的关键差异：**不再具备「会话超时后静默重登」能力**。
> 平台每次登录取票据都要一次图形验证码，后台无法替用户完成。

业务请求：

```text
页面调用 getScoreInfo / getExamInfo / …
  → 工具请求拦截器自动带 Cookie
  → 响应含「登录超时」「账号验证失败」
       → 清空 Cookie → 抛 JiaowuSessionExpiredError（不自动重登）
       → 界面提示「教务会话已过期，请重新登录」
```

对照旧版：

| 旧版                          | 新版                                              |
| ----------------------------- | ------------------------------------------------- |
| `loginJiaoWu`                 | `jiaowuLoginByCas`（口令版 `jiaowuLogin` 已废弃） |
| 直接在登录页 POST `check.asp` | 跳统一身份认证换 ticket 后回投 `caslogin.asp`     |
| 无验证码                      | 图形验证码，用户读图输入                          |
| 超时自动重登                  | 抛 `JiaowuSessionExpiredError`，用户手动重登      |
| `getPersonInfoFromJiaowu`     | `getPersonalInfo`                                 |
| AsyncStorage 明文密码         | SecureStore                                       |
| `profileStore` + ASP Cookie   | Zustand + SecureStore / MMKV + 工具 Cookie        |

## 4. 教务页门禁（产品行为）

- **无需登录（仅已进入 App 后）**：教务通知、竞赛通知。
- **需要登录**：学业进度、成绩、排名、考试安排、培养方案。
- **App 级**：未登录只能看到全局登录页，不能进入 Tab / 教务子页（见 `specs/登录门禁.md`）。教务首页 compact 登录仅作防御。
- 全局登录页与教务页内登录共用同一套「教务校验 → 档案 → 农屿 Token」流程。

## 5. 登出与清理

登出时至少清理：

- SecureStore 中的学号/教务密码
- App Token 与会话态
- 工具侧：`setCookie('')`，并清空 `LOGIN_DATA`（若工具后续提供显式 clear API 则改用）
- 教务相关 React Query 缓存（见《教务请求缓存方案》）

## 6. 注意事项

- 工具 Cookie / `LOGIN_DATA` 默认在**进程内存**；RN 杀进程后必须靠 SecureStore + 冷启动桥接恢复。
- Node 不校验教务密码；信任模型仍是「客户端已完成教务校验后再交档案」。
- **登录必须走统一身份认证**（`getJiaowuCaptcha` → 用户输验证码 → `jiaowuLoginByCas`）。
  `index.asp` + `check.asp` 口令链路已于 2026-10-23 被教务下线，`jiaowuLogin` 仅作回退对照。
- **验证码只能用户读图输入**。平台用这张图区分人与脚本；OCR 失败会让用户彻底卡在登录页。
  登录失败后必须换图（旧图一次性作废）。
- **不能静默重登**：拦截器命中「登录超时 / 账号验证失败」时清 Cookie 并抛
  `JiaowuSessionExpiredError`，由界面引导用户重新登录。这是本次改造的行为性变更。
- 会话 Cookie 只认 `ASPSESSIONID*`，来自 `caslogin.asp` 的 `Set-Cookie`。
- 非登录的教务请求 User-Agent 仍从运行时 `navigator.userAgent` 读取；可用 `setJiaowuUserAgent` 覆盖。无 `navigator` 时才回退。
- 本方案不包含：导入系统日历、课表模块鉴权细节（可复用同一套教务会话）。

## 8. 历史链路（已废弃，2026-08-14 调通）

> ⚠️ 教务处于 2026-10-23 取消首页账号密码登录，本链路随时会被彻底关闭。
> 仅作回退对照保留，**新代码不要使用**。当前链路见 §9。

> 2026-08-14 校园网真机调通。实现入口：`packages/nongyu-tool-jiaowu/core/login/index.ts` 的 `jiaowuLogin`。  
> **后续改登录必须保持本节顺序与约束**；浏览器一次 curl 抓包只能当对照，不能当可复用凭据。

### 8.1 正确顺序

```text
jiaowuLogin(user, pwd)
  1. 清空工具内存 Cookie
  2. GET  https://jiaowu.sicau.edu.cn/web/web/web/index.asp
         Referer = https://jiaowu.sicau.edu.cn/
         浏览器态 Header（Windows Edge 151 登录头）
         → 从 Set-Cookie 取 ASPSESSIONID* 写入内存（有则写；RN 读不到头也不要写空 Cookie）
         → 从 HTML hidden 解析 sign、hour_key（解析失败立刻中止）
  3. POST https://jiaowu.sicau.edu.cn/jiaoshi/bangong/check.asp
         Referer = 登录页 URL；Origin = https://jiaowu.sicau.edu.cn
         Content-Type = application/x-www-form-urlencoded
         body 字段顺序（与浏览器一致）：
           user、pwd、lb=S、submit=（空）、sign、hour_key
         maxRedirects = 0
  4. 判定成败（见 §8.3）→ 成功则 setCookie + setLoginData
```

登录页 hidden 形态示例（**value 每次打开都会变，禁止抄进代码**）：

```html
<input type="hidden" name="sign" value="（当页动态 hex）" />
<input type="hidden" name="hour_key" value="（当页动态长数字串）" />
```

解析须兼容 `name` / `value` 两种属性顺序，以及属性间多余空格。解析不到任一字段：抛「登录页未解析到 sign 或 hour_key」，**不得回退历史上冻过的固定值**。

### 8.2 Header 与 Cookie

- 登录 GET/POST 使用官网路径那套浏览器态头：`User-Agent`、`Accept`、`sec-ch-ua`、`Sec-Fetch-*`。拦截器**不得覆盖**登录请求已声明的 `User-Agent`。
- POST 有内存 Cookie 才写 `Cookie` 头；**禁止发空 Cookie**，以免盖掉 RN/OkHttp 原生 Cookie 罐。
- 非登录业务请求的 UA 仍走运行时 `navigator.userAgent`（`setJiaowuUserAgent` 可覆盖）。
- 会话 Cookie 只认 `ASPSESSIONID*`，来自当次登录页或 `check.asp` 的 `Set-Cookie`。

### 8.3 成败判定（HTTP 200 ≠ 成功）

教务响应是 GBK；axios `responseType: arraybuffer`，拦截器必须先 `decodeGbk` 再给 `jiaowuLogin` 看正文。`check.asp` **只解码、不走超时自动重登**，避免与 `jiaowuLogin` 循环。

| 现象                                                           | 判定                  |
| -------------------------------------------------------------- | --------------------- |
| 302 / 3xx                                                      | 成功                  |
| 200 + `location` / `window.location` 跳转                      | 成功                  |
| 200 + `alert('…')`（常伴随 `history.back` 或跳回 `index.asp`） | 失败，透出 alert 原文 |
| 正文含「登录失败 / 密码错误 / 账号不存在」                     | 失败                  |

常见失败原文：

- `验证失败，请通过正常链接重新登录！` → 没先打开登录页，或 sign / hour_key / Cookie 与当次页面不是同一会话。
- `用户名或密码错误！` → 凭据错，链路本身通常没问题。

成功后再 `getPersonalInfo()`（如 `xuesheng/dangan/banji/bjiben.asp`）。业务页若出现「登录超时」「账号验证失败」，拦截器清空 Cookie 后用 `LOGIN_DATA` 再走一遍本节链路并重放原请求一次。

### 8.4 踩过且已否决的做法

1. **冻一次浏览器 curl 的 Cookie / sign / hour_key 整包重放**  
   会话级字段，打开一次登录页就失效。即使 Header 与浏览器逐字相同，仍会得到「请通过正常链接重新登录」。
2. **只 POST check.asp、不先 GET index.asp**  
   教务按「正常链接」校验：必须先拿到当页 hidden 与 ASP 会话。
3. **用 HTTP 200 或「body 不是以 `<script` 开头的 string」当成功**  
   失败页也是 200，且未解码时是 ArrayBuffer，会被误判成功，随后档案页报「登录超时且已尝试过重新登录」。
4. **把开发机 Node `test.ts` 当唯一验收**  
   开发机访问 `jiaowu.sicau.edu.cn` 经常超时（校园网外不通）；验收以校园网真机为准。
5. **改 `core/` 源码却不 rebuild**  
   RN 加载的是 `packages/nongyu-tool-jiaowu/dist/index.js`。必须 `pnpm --filter nongyu-tool-jiaowu build`，必要时 `pnpm --filter nongyu-rn-app start -- --clear`。日志里 POST 的 `sign=` 应每次不同；若仍是某次冻死的 hex，就是 Metro 还在吃旧 dist。

### 8.5 仍须知情的限制

- RN 的 XHR 可能读不到 `Set-Cookie`；JS 内存 Cookie 为空时，依赖原生 Cookie 罐跟随后续请求，不要为了「对齐抓包」强行写空头。
- 登录头目前按 Windows 桌面 Edge 声明，请求实际从手机出网；以真机结果为准，不要为对齐桌面 TLS/HTTP2 指纹再改协议栈，除非再次失败。
- 文档与代码禁止写入真实教务密码；学号仅出现在调用方，不写进工具库常量。

## 9. 当前链路：统一身份认证（CAS）

> 2026-10-24 改造。实现入口：`packages/nongyu-tool-jiaowu/core/login/cas.ts`。

### 9.1 为什么必须改

教务处《关于调整教务管理系统登录方式的通知》（2026-10-23）：

> 现将取消普通用户在教务管理系统首页直接输入账号、密码登录的方式，
> 调整为「微信扫码登录」或「统一身份认证登录」方式。

对 App 的影响有三层：登录入口没了（§8 的 `check.asp` 下线）、多了图形验证码（无法后台代输）、
因此**静默自动重登必须移除**。

### 9.2 链路

```text
GET  https://jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp
  → 302 https://auth.sicau.edu.cn/sso/login
        ?appid=b54a2f27-f7ba-4b91-bbf0-3b2b12244d14
        &service=https://jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp

GET  https://auth.sicau.edu.cn/api/v1/captcha?appid=<教务 appid>
  → { code, id(uuid), requestId, data(加密) } → 解密得 data:image/png;base64,...

POST https://auth.sicau.edu.cn/api/v1/cas/login
  body: { appid, code(用户输入), number(学号), password, uuid }
  → { code, requestId, data(加密) } → 解密得 { callbackUrl, st, users:[{id}] }

GET  https://jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp
        ?ticket=<st>:<userId>&userId=<userId>
  → 302 + Set-Cookie: ASPSESSIONID*      ← 教务自己的会话，后续业务页复用
```

### 9.3 响应体解密（最容易卡住的地方）

平台的 `/api/v1/captcha`、`/api/v1/cas/login` 响应体**不是明文 JSON**，`data` 字段是密文：

```text
key        = MD5(requestId + ":sicau-cas")        // 32 hex → AES-128 key
raw        = base64decode(data)
iv         = raw[0:16]                            // 前 16 字节
ciphertext = raw[16:]
plain      = AES-128-CBC-decrypt(ciphertext, key, iv, NoPadding)
padLen     = plain[last]                          // 自定义填充：尾字节 = 填充长度
json       = JSON.parse(plain[0 : -padLen])
```

注意：

- 用的是 **NoPadding**，不是 PKCS#7；尾部填充靠最后一字节自行剥离。
- `requestId` 与 `data` 必须取自**同一个响应**，混用会解出乱码。
- 失败响应（如「验证码错误」）的 `data` 是 `null`，此时不要解密。
- RN 没有 `node:crypto`，包内用 `crypto-js`（纯 JS）实现，见 `cas.ts`。

### 9.4 关键常量（不得随意改）

| 常量                  | 值                                                        | 来源                             |
| --------------------- | --------------------------------------------------------- | -------------------------------- |
| 教务 appid            | `b54a2f27-f7ba-4b91-bbf0-3b2b12244d14`                    | `caslogin.asp` 的 302 `Location` |
| service / callbackUrl | `https://jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp` | 同上                             |
| 加密盐                | `:sicau-cas`                                              | 平台前端 bundle                  |
| Cookie 前缀           | `ASPSESSIONID`                                            | 教务 ASP 会话                    |

### 9.5 真机验收踩到的两个坑（都已修，改登录前必读）

**坑 1：平台返回的 `callbackUrl` 里已经带了 `?ticket=ST:xxx`**

```
callbackUrl(原样) = https://jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp?ticket=ST%3A7RAX...%3D
```

平台前端是 `searchParams.set("ticket", st + ":" + userId)` —— **覆盖**。
如果像字符串拼接那样再 `&ticket=` 追加一次，URL 会变成：

```
?ticket=ST%3A7RAX...&ticket=ST%3A7RAX...%3A201690&userId=201690
         ↑ 教务读的是这个，缺少 ":userId" 后缀 → 校验失败
```

症状：登录接口 200 成功，但业务页一律 302 回 `jiaoshi/bangong/index.asp`。
实现见 `buildCallbackUrl()`：先剔除同名 `ticket` / `userId` 再写回。

**坑 2：教务回调是两步，会话在第二跳才建立**

```
GET caslogin.asp?ticket=ST:xxx:userId&userId=…   → 302 ../bangong/check_cas.asp?sign=…
GET check_cas.asp?sign=…                          → 302 首页 + Set-Cookie: ASPSESSIONID*   ← 会话在这
```

停在第一跳（`maxRedirects: 0` 且不手动跟）只会拿到 302，**一个新 Cookie 都没有**，
于是「登录成功但拿不到有效会话」。实现见 `resolveRedirect()` + 循环跟随（`CAS_MAX_REDIRECTS = 5`）。

> 教训：CAS 客户端不能假设「回调一次就完事」，也不能依赖 URL 拼接构造查询参数 ——
> 平台的 JS 用 `URLSearchParams.set`，客户端必须等价实现。

### 9.6 踩过且已否决的做法

1. **对验证码做 OCR 自动识别**
   识别错一次就白跑一次请求，用户还得手动救场；验证码本就是平台用来区分人与脚本的，
   识别率永远达不到可用。结论：验证码一律让用户读图输入。
2. **登录失败后继续用同一张验证码重试**
   验证码一次性，失败即作废。`jiaowuLoginByCas` 返回 `needRefreshCaptcha`，
   界面收到就必须换图并清空输入。
3. **保留拦截器里的静默自动重登**
   没有验证码就无法后台登录，保留只会产生一串必然失败的请求 + 误导性日志。
4. **用 `caslogin.asp` 的初始 Set-Cookie 当登录结果**
   首次 GET（无 ticket）只是建立会话，真正带身份的是带 ticket 回投之后的响应，
   两者要用同一个 ASP 会话串起来（见 `mergeCookiePairs`）。

### 9.7 验证方式

# 2) 登录接口契约（错误验证码应返回 500 + 验证码错误）

  -H 'Content-Type: application/json' \
  -d '{"appid":"b54a2f27-f7ba-4b91-bbf0-3b2b12244d14","code":"0000","number":"<学号>","password":"<密码>","uuid":"<uuid>"}'

# 3) 教务 CAS 入口跳转是否仍指向同一 appid / service
curl -sI 'https://jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp' | grep -i location

## 10. 自动登录（验证码 OCR）

目标：用户只需提供一次学号密码，之后由服务端自动完成登录、拿到教务会话，**不再要求用户读验证码**。

### 10.1 先排除的三条「免验证码」路（都试过，不通）

| 尝试                                                 | 结果                       |
| ---------------------------------------------------- | -------------------------- |
| CAS REST（`POST /sso/v1/tickets`，标准免验证码换票） | 404，平台未开启            |
| 登录返回的 `tgt` 当 `CASTGC` cookie 换 ticket        | 4 种写法全部 302 回登录页  |
| 复用 CAS 持久登录态（HttpOnly cookie 免登）          | 无持久 SSO，仍要求重新登录 |

结论：**唯一入口就是「密码 + 验证码」**，自动化必须自己解决验证码。

### 10.2 验证码特性与识别

实测样本（40 张）：240×80 PNG，**4 位纯数字**，字符轻微扭曲 + 一条横向波浪干扰线 + 少量噪点。

用 `ddddocr`（onnx，纯离线）：

| 预处理                                    | 6 张人工标注样本的准确率 |
| ----------------------------------------- | ------------------------ |
| 原图 + 限制字符集                         | 3/6                      |
| **中值滤波 MedianFilter(3)** + 限制字符集 | **5/6**                  |
| 二值化 / 放大 / 锐化 / autocontrast       | 3/6（无改善）            |

关键：**中值滤波去干扰线**是有效手段，其他花哨预处理反而变差。

单次约 83%，配合换图重试：`1 - 0.17^5 ≈ 99.99%`（默认重试 5 次）。

### 10.3 为什么 OCR 跑在 Python 而不是 Node

`ddddocr` 的 onnx 模型在 Node 侧可以完全复现——用 `onnxruntime-node` 加载 `common_old.onnx`（注意：**默认模型是 `common_old.onnx`，不是 `common.onnx`**），
喂同一份输入张量时，Node 与 Python 的输出**逐值一致**（最大差异 0.000000）。

但**图像预处理**对不上：PIL 的 LANCZOS resize 与 libvips（sharp）的重采样有细微差异，
同批样本 Node 侧只有 3/6，Python 侧 5/6。与其复刻 PIL 的重采样内核，不如直接调用 Python 实现。

> 若将来要摆脱 Python 依赖：需要按 PIL 的 `Resample.c` 复刻 separable LANCZOS（support=3、系数归一化、边界处理），
> 或换用对预处理不敏感的模型。

### 10.4 服务端实现

`apps/nongyu-node-server/src/modules/jiaowu-hosted/`

| 文件            | 职责                                                                     |
| --------------- | ------------------------------------------------------------------------ |
| `ocr/worker.py` | 常驻 ddddocr 进程，行协议：每行 base64 → 每行结果                        |
| `ocr/client.ts` | worker 生命周期：懒启动、串行队列、超时重启、不可用降级                  |
| `autoLogin.ts`  | `autoLogin({studentNo, password})`：取图 → OCR → CAS 登录 → 失败换图重试 |

链路复用 `nongyu-tool-jiaowu` 的 `getJiaowuCaptcha` / `jiaowuLoginByCas`（与客户端同一份实现）。

降级语义：识别器不可用时 `autoLogin` 返回 `ocrUnavailable: true`，
上层应回落到「客户端手动输入验证码」，而不是报登录失败。

## 11. 登录方式矩阵（用户自选）

登录页提供四种入口，用户自己选。只有「自动登录」是免验证码的，其余都是非自动：

| 方式         | 用户操作                                       | 是否经过服务端存密码   | 是否免验证码             |
| ------------ | ---------------------------------------------- | ---------------------- | ------------------------ |
| **自动登录** | 勾选授权，输一次账密                           | 是（AES-256-GCM 加密） | ✅ 是                    |
| 账密         | 每次输账密 + 读图形码                          | 否                     | 否                       |
| 手机验证码   | 图形码 → 收短信 → 输短信码                     | 否                     | 否（发短信前仍需图形码） |
| 微信扫码     | 浏览器打开教务系统扫码（需先绑「川农微教务」） | 否                     | 否（人工确认）           |

### 11.1 服务端接口

| 方法   | 路径                                | 说明                                           |
| ------ | ----------------------------------- | ---------------------------------------------- |
| GET    | `/api/app/jiaowu/hosted`            | 托管状态；`available=false` 时客户端隐藏入口   |
| POST   | `/api/app/jiaowu/hosted`            | 开启托管：**立刻真登录一次**校验密码，错则 400 |
| DELETE | `/api/app/jiaowu/hosted`            | 关闭托管：删行，不留副本                       |
| POST   | `/api/app/jiaowu/hosted/login`      | 用托管凭据换会话，命中 10 分钟缓存直接返回     |
| POST   | `/api/app/jiaowu/hosted/invalidate` | 教务判定会话失效时清缓存，下次真重登           |

鉴权走 `requireAppAuth`，开启/换会话均受 `loginRateLimit` 限制。

### 11.2 凭据存储

```sql
-- migrations/013_jiaowu_credentials.sql
jiaowu_credentials(user_id PK, student_no, password_cipher, enabled, last_login_at, last_error, ...)
```

- 加密：**AES-256-GCM**，密文格式 `v1.iv.tag.cipher`（base64），带认证标签防篡改
- 密钥：环境变量 `JIAOWU_CREDENTIAL_KEY`（64 位 hex 或 base64 解出 32 字节）
- 密钥留空 = 托管能力整体关闭，客户端 `available=false` 自动隐藏入口
- 轮换密钥会让已托管凭据全部失效，用户需重新开启（`needsReauth=true`）

> 为什么不是 bcrypt：这里要**还原明文**去登录教务，bcrypt 是单向哈希，做不到。

### 11.3 客户端
